# New Dash Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build an independent, source-first macOS application that reads one FoF badge over USB and provides the approved New Dash live, map, history, diagnostics, and safe-control browser experience.

**Architecture:** A single Python process owns the serial device, parses the badge's newline-framed machine records, maintains an in-memory current snapshot, persists bounded observations in SQLite, and serves a loopback-only vanilla web application. Python's standard library provides every service except the PySerial device adapter; the existing `backend/` is neither imported nor modified.

**Tech Stack:** Python 3.11+, PySerial 3.x, `unittest`, SQLite, `ThreadingHTTPServer`, plain HTML/CSS/ES modules, vendored Leaflet client assets, OpenStreetMap tiles when online.

## Global Constraints

- New Dash lives entirely under top-level `new-dash/`, apart from its root README entry and these Superpowers documents.
- The existing `backend/` must have no diff.
- macOS and one uplink ESP32-S3 badge are the only tested runtime platform/device combination in v1.
- PySerial is the only Python runtime dependency; there is no Node runtime or frontend build step.
- The service binds only to `127.0.0.1`; it never enables permissive CORS.
- Automatic USB selection accepts exactly one physical Espressif
  `0x303A:0x1001` candidate after macOS alias deduplication; explicit paths
  still require post-write `FOF_PONG` verification.
- Serial settings are nominal 115200 baud, DTR false and RTS false before open,
  exclusive access when supported, and newline-terminated UTF-8 writes.
- Status polling is two seconds, stale status is six seconds, silent-session reconnect is twelve seconds, and reconnect backoff is capped at ten seconds.
- USB lines are capped at 64 KiB and only `FOF_PONG`, `FOF_DET`, `FOF_STATUS`, `FOF_CTL_OK`, and `FOF_CTL_ERROR` are accepted.
- Outgoing commands are compact finite JSON capped at 2047 bytes before their
  newline; one control is in flight, and a timeout forces re-verification.
- Explicit Remote ID means source ID 0 / `ble_rid` or source ID 3 / `wifi_rid`; DJI vendor-IE remains separate drone evidence.
- SQLite history defaults to 30 days and 50,000 total observations, with neither zero nor a negative value accepted as an unbounded setting.
- Only display navigation, complete theme apply/reset, and complete display-policy apply/reset can write to the badge. Firmware, reboot, bootloader, recovery mutation, generic controls, and raw serial writes are absent.
- Dashboard text originating from USB is rendered with DOM text APIs, never HTML interpolation.
- Every behavior change follows red-green-refactor: write one focused failing test, observe the expected failure, implement the minimum behavior, and rerun the focused plus accumulated suite.

- [ ] **Step 5: Implement the line framer and detection parser minimally**

`LineFramer` buffers bytes, enters a dropping state after the configured limit,
resets that state only at CR/LF, and decodes a completed line using
`errors="replace"`. `parse_machine_line` returns `None` before attempting JSON
unless a recognized prefix is present.

Lock the production boundary explicitly: a 65,536-byte line is accepted, byte
65,537 enters discard-until-delimiter, and a CRLF pair acts as one logical
delimiter. Count invalid UTF-8 by attempting strict decode before replacement.

`DetectionEvent.from_payload` validates the payload is an object, coerces only
the firmware's documented scalar fields, uses source `unknown_<id>` for future
integer IDs, and prefers this stable-key order:

```python
return self.badge_entity_key or f"{self.source}:{self.detection_id}"
```
