# What Friend or Foe could do on iPhone

**Recommendation.** Start with a foreground **Privacy → Recorders** scan. Show the device name or service that matched, signal strength, when it was seen, and “Recording status unknown.” Keep the nearby devices, everyday accessories and beacon groups people already know from Android. Distinguish observations made by this iPhone from reports supplied by a scanner. This is a feasibility review as of November 2026. Device coverage still needs measurements on physical iPhones.

| Feature | What an iPhone version could offer |
| --- | --- |
| **Plaud and other personal recorders** | Core Bluetooth can deliver a local name, advertised service IDs, service data and manufacturer data. Plaud matching depends on a visible name such as `PLAUD` or `NotePin`. Omi and Limitless can also match a distinctive advertised service. Renaming a device, connecting it to its owner’s phone or putting it away can change what a bystander sees. Seeing a recorder gives no indication of whether its microphone is active. [Apple advertisement fields](https://developer.apple.com/documentation/corebluetooth/advertisement-data-retrieval-keys) · [Android recorder rules and evidence](personal-ai-recorders.md) · [Plaud pairing guide](https://support.plaud.ai/hc/en-us/articles/50841107617433-Bind-the-device) |
| **Cameras, glasses, audio accessories and trackers** | Port rules that use fields iOS exposes, then verify each family. Core Bluetooth supplies an Apple-assigned peer identifier, so Android rules that depend on a nearby device’s Bluetooth MAC address or its manufacturer prefix need another source. Foreground AirTag and other tracker discovery has been demonstrated. Apple delivers its own unwanted-tracking alerts separately. Keep AirPods and routine accessory sightings grouped, with details on demand. [Apple peer identifiers](https://developer.apple.com/documentation/corebluetooth/cbpeer/identifier) · [AirGuard study, §2.4](https://petsymposium.org/popets/2024/popets-2024-0082.pdf) · [Apple unwanted-tracking alerts](https://support.apple.com/en-us/119874) |
| **iBeacon groups** | Core Location can range beacons with a known proximity UUID, then group sightings by UUID, major and minor. Apple filters iBeacon packets out of general Core Bluetooth discovery. To show previously unknown venue UUIDs, use an external scanner report. [Apple iBeacon guide, p. 4](https://developer.apple.com/ibeacon/Getting-Started-with-iBeacon.pdf#page=4) |
| **Wi-Fi privacy alerts** | A scanner or backend can supply the observed SSID, security type and reason for an alert. A regular iPhone app cannot list nearby access points, capture probe requests or search surrounding networks for a camera setup SSID. An eligible app can request information about the network the phone has joined. Wi-Fi Aware on supported iPhones provides connections to participating peers. [Apple Wi-Fi API overview](https://developer.apple.com/documentation/technotes/tn3111-ios-wifi-api-overview) · [Wi-Fi Aware](https://developer.apple.com/documentation/wifiaware) |
| **Aircraft, maps and drones** | Existing aircraft feeds, flight history and reference art can power a map. Local Bluetooth drone Remote ID is plausible for compatible broadcasts and needs transmitter testing. Wi-Fi Remote ID and broader radio coverage require an external receiver. Label a network-fed aircraft position and a locally received drone broadcast separately. [MapKit](https://developer.apple.com/documentation/mapkit/mapkit-for-swiftui) · [Dronetag’s iOS receiver experience](https://help.dronetag.com/drone-scanner/) |
| **Camera, sound and alerts** | A camera overlay and user-started microphone analysis are feasible with permission. Lens reflections and near-ultrasonic pickup need model-by-model tests before drawing conclusions from them. Bluetooth signal strength can show a trend as the user moves. Precision direction requires compatible, participating hardware. Background BLE discovery is filtered and can coalesce sightings. A name-only recorder may vanish when the screen locks. Treat locked-screen alerts as a separate capability to measure. [Capture permission](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media) · [Nearby Interaction](https://developer.apple.com/documentation/nearbyinteraction) · [Apple background scanning guidance](https://developer.apple.com/forums/thread/815189) |

### What it would take

1. **Measure the recorder experience first.** Borrow a Plaud and a service-advertising recorder such as Omi. Compare what two iPhone models and Android see during pairing, idle, active recording and connection to the owner’s phone. Repeat with the app visible and the screen locked. Include ordinary earbuds and a renamed device. Record the fields each platform actually receives and the cases it misses.
2. **Use the existing data where it fits.** Reuse documented signatures, sample observations, reference assets and backend response formats. Build the iPhone screens, permission flows, Bluetooth discovery and local history with Apple APIs. A configured backend could deliver scanner findings over the network. The badge’s current local HTTP endpoint exposes read-only status, and the Android control path uses USB serial. A direct iPhone badge connection for live detections or controls would need a separately supported protocol and hardware validation. [Badge transport contract](badge/README.md) · [Apple USB accessory guidance](https://developer.apple.com/forums/thread/802640) · [Local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)
3. **Validate the release promises.** Use the hardware results to name supported products and operating modes. Request Bluetooth for scanning and additional permissions only when their features are opened. Document which observations stay on the phone and when an optional map, aircraft feed or scanner connection sends location or network data. Test with TestFlight and give App Review a reproducible path through hardware-dependent screens. [TestFlight](https://developer.apple.com/testflight/) · [App privacy details](https://developer.apple.com/app-store/app-privacy-details/) · [App Review guidelines](https://developer.apple.com/app-store/review/guidelines/)
